# 공통 엔지니어링 규칙 (스택 무관)

모든 AIRISS 레포에 적용되는 기본 규칙.
※ 표준 원본: claude-code-standard v0.12 — 이 파일은 레포에서 직접 수정하지 말 것(표준 레포 PR로).

## 핵심 행동 원칙
AI는 코드를 못 짜는 게 아니라 **너무 많이, 너무 빨리 짜는 게** 문제다. 아래는 그 브레이크다.

1. **코딩 전에 생각한다 (Think Before Coding)** — 추측하지 않는다. 모르면 모른다고 하고, 방법이 여러 개면 **선택지와 트레이드오프를 먼저 드러낸 뒤** 진행한다. 혼란을 감추고 일단 짜지 않는다.
2. **단순함 우선 (Simplicity First)** — 문제를 푸는 **최소한의 코드**만. 미래를 위한 추측성 추상화나 일반화를 넣지 않는다.
3. **외과적 수정 (Surgical Changes)** — **요청 범위만** 건드린다. 옆 코드를 겸사겸사 고치지 않는다. 별도 개선거리는 따로 제안한다.
4. **목표 기반 실행 (Goal-Driven)** — 성공 기준을 정의하고, **검증될 때까지** 반복한다. 검증을 사용자의 현장 시험에 넘기지 않는다.

**새 코드를 쓰기 전 사다리** — 먼저 걸리는 데서 멈춘다.
① 꼭 있어야 하나 ② 이 레포에 이미 있나 ③ 표준 라이브러리나 쓰고 있는 패키지에 있나 ④ 한 줄로 되나 ⑤ 그래도 남으면 동작하는 최소 구현.
검증, 에러 처리, 보안, 레포가 강제하는 규칙은 깎는 대상이 아니다.

## 사실 확인 — 다른 규칙보다 먼저
- 코드나 동작을 말하기 전에 그 파일을 끝까지 연다. 파일명이나 클래스명만 보고 동작을 짐작하지 않는다.
- 주장에는 근거(`경로:라인`, 검색 결과, 빌드와 테스트 출력)를 붙인다. 못 붙이면 "확인 안 함"이라고 쓴다.
- 없다고 말할 때는 어떻게 찾았는지 밝힌다. 세는 명령은 샘플로 먼저 시험한다. 0건은 깨끗함이 아니라 무응답일 수 있다.
- 에이전트나 도구가 준 결과는 핵심을 직접 다시 확인한다. 중요한 판정은 `verifier` 에이전트에게 반증을 맡긴다.
- 심각도를 부풀리지 않는다. 관측된 적 없으면 "이론상"이라고 쓰고, 그걸 고치려고 새 위험을 들이지 않는다.

## 작업 순서
- 큰 작업(새 기능이나 구조 변경)은 **조사 → 플랜 → 승인 → 구현 → 검증** 순서로 간다. 조사 없이 코딩을 시작하지 않는다. → `/plan-feature`
- 작업 중 플랜과 달라지는 지점이 생기면 **말없이 바꾸지 말고** 알린다.
- 한 세션에 무관한 작업을 섞지 않는다. 목적이 바뀌면 새 세션으로.

## 응답과 소통
- 사용자에게는 **한국어**로 답한다(기술 용어는 영어 그대로 허용).
- 확실하면 행동한다. 이미 정해진 것을 다시 묻지 않는다.
- 파일 참조는 클릭 가능한 경로 형식으로(`경로:라인`).

## 코드 작성
- **주변 코드를 닮게**: 네이밍, 주석 밀도, 관용구를 파일의 기존 스타일에 맞춘다.
- 요청받지 않은 대규모 리팩토링을 끼워 넣지 않는다.
- 추측성 주석/과도한 방어 코드로 부풀리지 않는다.

## 코드 품질 (지킬 것만 짧게)
- **이름이 설명이 되게.** 주석으로 설명해야 한다면 이름이 틀린 것이다. 축약어, `data`, `temp` 같은 무의미한 이름을 쓰지 않는다.
- **함수는 한 가지 일만.** 중첩이 깊어지면 이른 반환(early return)으로 편다.
- **중복은 세 번째에 추출한다.** 두 번은 우연, 세 번이면 패턴. 한 번 보고 미리 추상화하지 않는다.
- **죽은 코드는 지운다.** 주석 처리해서 남기지 않는다 — git 이력에 있다.
- **실패를 성공처럼 보이게 하지 않는다.** 빈 catch 금지, 처리 못 할 예외는 올려보낸다. 장비, DB, 외부 API로 나가는 호출은
  보내기 전에 화면 값을 먼저 바꾸지 않고, `?.` 로 호출을 건너뛰지 않는다. 호출한 쪽이 실패를 알아야 한다.
- **같은 이름을 다른 뜻으로 두 번 쓰지 않는다.** 외부 제품은 그 회사가 실제로 파는 이름을 확인해서 쓴다.
- **주석은 코드가 답 못 하는 것만 쓴다.** 함정, 호출 순서 의존, 값을 고른 근거. `왜:` 라벨, 옛 동작 회고, 구분선은 쓰지 않는다. 틀린 주석은 없는 주석보다 나쁘다.
- **다른 레포나 브랜치에서 옮길 때** 같은 문자열이 여러 번 나오면 위치를 특정하고, 옮긴 뒤 원본이 추가한 줄이 다 들어왔는지 기계적으로 대조한다.
- **매직 넘버와 하드코딩 문자열 금지.** 상수, 설정, 리소스를 참조한다.
- 리팩토링은 **동작을 바꾸지 않는다.** 버그를 발견하면 따로 알리고 따로 고친다. → `/refactor`

## 프로젝트 구조
- 새 파일은 **이 레포의 기존 구조가 정한 자리**에 둔다. 새 최상위 폴더를 임의로 만들지 않는다.
- 어디에 둘지 애매하면 **가장 비슷한 기존 기능이 어디 있는지 먼저 찾는다.** → `/scaffold-feature`
- 의존 방향을 거스르지 않는다(UI → 도메인 → 인프라 등 이 레포의 계층 규칙).
- 구조를 바꿔야 한다면 코드보다 먼저 말한다.

## 커밋 (요청 시에만)
- 사용자가 명시적으로 요청할 때만 커밋/푸시한다. → `/commit`, `/open-pr`
- **기본 브랜치에 바로 커밋할지는 레포 `CLAUDE.md` 가 정한다.** 정하지 않았으면 브랜치를 먼저 만든다.
- `git add -A`, `git push --force` 를 쓰지 않는다. 다른 세션의 작업이 딸려 들어가거나 이력이 사라진다.
- 커밋 메시지는 이 레포 관례를 따르고, 없으면 Conventional Commits(`feat:` `fix:` `refactor:` `docs:` `test:` `chore:`). **무엇을 했는지가 아니라 무엇이 달라지는지**를 쓴다.
- 한 커밋에 서로 다른 목적을 섞지 않는다.
- 훅이 실패하면 우회(`--no-verify`)하지 말고 원인을 고친다.

## 검증
- 변경 후 "된다"고 말하기 전에 실제로 빌드/실행/테스트로 확인한다.
- 테스트가 실패하면 실패했다고 출력과 함께 정직하게 보고한다.
- 건너뛴 단계가 있으면 건너뛰었다고 말한다.
- VS Code에서 작업 중이면 편집 직후 **IDE 진단(Problems 패널)** 을 확인한다(`mcp__ide__getDiagnostics`). 컴파일러를 돌리기 전에 타입 오류와 누락 import를 먼저 잡을 수 있다.

## 문장과 문장 부호
답변, 문서, 화면 문구, 커밋 메시지 모두에 적용한다.
- 가운뎃점(U+00B7)으로 나열하지 않는다. 두 개는 `A와 B`, 셋 이상은 쉼표나 대표하는 말 하나, 화면에서는 칸이나 줄을 나눈다. 앞뒤를 띄운 가운뎃점 구분자는 특히 쓰지 않는다.
- `소제목 — 세부 나열` 처럼 줄표로 잇지 않는다.
- 예외: 굳어진 고유 표기, 남의 글 인용, 코드와 데이터 값.
- 지시문이나 기존 문서에 가운뎃점이 있으면 모델이 문체를 따라 한다. 규칙, 스킬, 문서를 새로 쓸 때도 쓰지 않는다.

## 보안
- 비밀(키, 토큰, 비밀번호)을 코드/설정/문서에 하드코딩하지 않는다.
- 커밋 전 변경분에 시크릿이 섞였는지 확인한다.
- 되돌리기 어렵거나 외부로 나가는 작업은 먼저 확인받는다.
