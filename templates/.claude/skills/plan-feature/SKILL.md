# /plan-feature <무엇을 만들지>

$ARGUMENTS 를 **짜기 전에 조사하고 설계한다.** 코드를 건드리지 않는다.

> 왜: AI는 코드를 못 짜는 게 아니라 **너무 많이, 너무 빨리 짜는 게** 문제다.
> 5분 조사가 몇 시간 재작업을 막는다.

## 1. 조사 (코드를 먼저 읽는다)

- 이 레포에서 **가장 비슷한 기존 구현**을 찾는다. 없으면 없다고 말한다.
- 건드리게 될 파일, 모듈, 경계를 나열한다. 영향 범위를 과소평가하지 않는다.
- 기존 관례를 확인한다: 폴더 구조, 네이밍, 등록/라우팅 방식, 테스트 위치, 에러 처리 패턴.
- **모르는 것은 모른다고 적는다.** 추측으로 메우지 않는다.

## 2. 선택지와 트레이드오프

방법이 하나뿐이면 그렇게 말하고 넘어간다. 둘 이상이면 **비교해서 보여준다**:

| 안 | 장점 | 단점 | 영향 범위 |
|---|---|---|---|

그리고 **하나를 추천한다.** 나열만 하고 사용자에게 떠넘기지 않는다.

## 3. 플랜

```
목표:        (완료 판정 기준 — "무엇이 되면 끝인가")
변경할 파일:  (경로 + 각각 무엇을 하는지 1줄)
새로 만들 것: (경로 + 역할)
검증 방법:    (어떤 명령/화면으로 확인하는가 — 여기서 정해두지 않으면 나중에 "된 것 같다"로 끝난다)
안 하는 것:   (범위 밖으로 명시. 스코프 크립 방지)
위험:        (되돌리기 어려운 것, 장비, DB, 마이그레이션이 걸린 부분)
```

- 큰 작업이면 플랜을 `docs/10_Raw_Sources/plan-<이름>.md` 로 저장할지 사용자에게 묻는다.
- 3단계 이상이면 **커밋 단위로 쪼갠다**(각 단계가 독립적으로 검증 가능하게).

## 4. 승인 후에만 구현

플랜을 제시하고 **멈춘다.** 사용자가 승인하면 그때 구현을 시작한다.
구현 중 플랜과 달라지는 지점이 생기면 **말없이 바꾸지 말고** 알린다.

> 💡 VS Code에서는 Plan 모드(모드 인디케이터 클릭)로 시작하면 플랜이 Markdown 문서로 열려
> 인라인 코멘트로 피드백할 수 있다. 이 스킬과 함께 쓰면 좋다.
