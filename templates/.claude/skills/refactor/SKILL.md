# /refactor <대상>

$ARGUMENTS 를 리팩토링한다. **원칙: 동작은 그대로, 구조만 바꾼다.**

## 0. 먼저 멈추고 확인

- **왜 지금 리팩토링하는가?** 실제 통증(버그 유발, 수정이 매번 어려움, 중복이 계속 어긋남)이 없으면
  하지 않는다. "더 깔끔해 보여서"는 이유가 아니다.
- **요청 범위를 넘지 않는다.** 옆 코드를 겸사겸사 고치지 않는다. 발견한 다른 개선거리는 **따로 목록으로 제안**한다.

## 1. 안전망 확보

리팩토링은 **되돌아갈 수 있어야** 시작할 수 있다.

- 이 코드를 검증할 수단이 있는가? 테스트, 빌드, 실행 화면 중 최소 하나.
- 없으면 **먼저 특성화 테스트(현재 동작을 그대로 고정하는 테스트)를 만들 것을 제안**한다.
  자동 테스트가 어려운 영역(WPF 화면, 장비 연동)이면 **수동 확인 절차를 글로 적어두고** 진행한다.
- 시작 전 커밋이 깨끗한지 확인한다(되돌릴 지점).

## 2. 작은 단계로

한 번에 하나씩. 각 단계 후 **검증을 돌린다.**

흔한 단계:
- 중복 제거 → 기존 유틸이 이미 있는지 **먼저 찾는다**(새로 만들기 전에)
- 긴 함수 분리 → 이름이 설명이 되게. 주석으로 설명해야 한다면 이름이 틀린 것
- 이름 개선 → 무엇인지가 아니라 **무엇을 위한 것인지**
- 조건문 정리 → 이른 반환(early return)으로 중첩 줄이기
- 죽은 코드 삭제 → **커밋 이력에 남아 있으니** 주석 처리하지 말고 지운다

## 3. 하지 말 것

- ❌ **추측성 추상화** — "나중에 필요할 것 같아서" 만드는 인터페이스, 제네릭, 설정 옵션
- ❌ 동작 변경을 슬쩍 끼워 넣기 — 버그 발견하면 **따로 알리고 따로 고친다**
- ❌ 공개 시그니처나 기존 테스트를 깨기
- ❌ 한 커밋에 리팩토링 + 기능 변경 섞기

## 4. 마무리

- 검증을 **실제로 돌리고** 결과를 보여준다. 실패하면 실패했다고 말한다.
- 무엇이 어떻게 좋아졌는지 1~3줄로 요약한다. "깨끗해졌다"가 아니라 구체적으로.
- 발견했지만 손대지 않은 개선거리를 목록으로 남긴다.
