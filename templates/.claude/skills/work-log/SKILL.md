# /work-log [날짜 또는 기간]

팀 업무 시트의 **[업무 상세 내용(일일로그)] 칸에 들어갈 텍스트만** 만든다.
날짜, 이름, 프로젝트명, 카테고리, 상태, 성과 칸은 **채우지 않는다**(사람이 채우거나, 물어보면 그때 답한다).

## 1. 범위 정하기

- 인자가 날짜면 그 날, 기간이면 그 기간. 인자가 없으면 **오늘**.
- 연도가 없으면 올해. "이번주"면 월요일~오늘.
- 작성자는 기본적으로 **현재 git 사용자**. 다른 사람 것이면 사용자가 지정한다.

## 2. 근거 수집 — 추측하지 않는다

```bash
# Git Bash
git log --all --no-merges --author="$(git config user.name)" \
  --since="2026-08-28 00:00" --until="2026-08-28 23:59" \
  --pretty=format:"%h | %ad | %s" --date=format:"%m-%d %H:%M"
```
```powershell
# PowerShell (Git Bash 없는 환경)
git log --all --no-merges --author="$(git config user.name)" --since="2026-08-28 00:00" --until="2026-08-28 23:59" --pretty=format:"%h | %ad | %s" --date=format:"%m-%d %H:%M"
```

**미커밋 변경은 그날 고친 파일만 친다.** 수정 시각이 그날이 아닌 파일은 뺀다. 남은 것은 `~ 진행 중` 줄로 쓴다.

```bash
git status --porcelain | cut -c4- | while read -r f; do [ "$(date -r "$f" +%F)" = "2026-08-28" ] && echo "$f"; done
```
```powershell
git status --porcelain | ForEach-Object { $_.Substring(3) } | Where-Object { (Test-Path $_) -and (Get-Item $_).LastWriteTime.ToString('yyyy-MM-dd') -eq '2026-08-28' }
```

- 커밋 제목만으로 **무엇이 달라졌는지** 모르겠으면 `git show <hash> --stat` 로 본문과 변경 파일을 본다.
- 파일명이나 클래스명으로 **내용을 추측하지 않는다.** 모르면 사용자에게 묻는다.

**커밋이 없거나 부족하면 반드시 물어본다.** 이 팀의 업무에는 커밋이 남지 않는 것이 많다 —
기기 제작, 납품 준비, 물품 검수, 문서 작성, 인증 서류, 회의, 기술 지원, 센서 조사 등.
커밋이 없다고 "작업 없음"으로 단정하지 말 것.

## 3. 프로젝트별로 나눈다

시트는 **프로젝트가 다르면 행이 나뉜다**(같은 사람, 같은 날이어도).
커밋을 프로젝트 단위로 묶고, **블록을 나눠서** 출력한다. 어느 프로젝트인지 애매하면 물어본다.

## 4. 작성 규칙 (이 스킬의 핵심)

- **한 줄은 한 주제.** 주제는 영역(같은 화면, 같은 기능, 같은 장비 동작)으로 나눈다. 커밋 1개당 1줄이 아니다.
  같은 영역 커밋은 종류가 달라도 **한 줄로 합치고**, 한 커밋이 두 영역을 건드렸으면 두 줄로 나눈다.
- **블록당 내용 7줄, 줄당 32자**(공백 포함). 주제를 우선순위 순으로, 같은 우선순위는 커밋 많은 순으로 놓는다.
  7개를 넘으면 앞 6개만 쓰고 나머지는 `그 외 ○○와 ○○ 개선 여러 건` 한 줄로 합친다. ○○에는 남은 영역 이름을 커밋 많은 순으로 두 개까지 쓴다.
- **우선순위**: 신규, 안전과 거짓 성공, 개선, 결함, 문서. 한 주제에 여러 종류가 섞이면 가장 높은 종류를 따른다.
- **명사형으로 끝낸다.** `~ 추가` `~ 수정` `~ 정리` `~ 개선` `~ 재구현` `~ 문서화` `~ 보강`.
  "했습니다", "~하였음" 같은 서술형을 쓰지 않는다.
- **무엇이 달라졌는지**를 쓴다. 파일명, 클래스명, 함수명, 변수명은 쓰지 않는다.
  - ❌ `MainCanvasViewModel 리팩토링`
  - ✅ `캔버스 화면 코드 구조를 기능 축으로 정리`
- **팀이 쓰는 말은 그대로 쓴다.** V/H, 캔버스, 톤, 드립, 선명도, Detector, PLC, SAT, 스캔 등은 팀 공용어다.
  반대로 코드 안에서만 쓰는 이름, 즉 클래스, enum, 필드명은 풀어 쓴다.
- **괄호를 쓰지 않는다.** 부연을 괄호에 넣지 말고 **줄을 나누거나 문장으로 푼다.**
  - ❌ `알림 오작동 수정 (새 알림이 비상해제를 부르던 것 등)`
  - ✅ `새 알림이 비상해제를 부르던 알림 오작동 수정`
  - ❌ `영상 톤 보정 성능 개선 (감마, 대조, 밝기를 한 번에 적용)`
  - ✅ `감마, 대조, 밝기를 한 번에 적용해 톤 보정 개선`
  - 32자에 안 들어가면 부연을 빼고 무엇이 달라졌는지만 남긴다.
- **버그 수정은 "무엇이 안 되던 것"을 밝힌다.** 증상 중심으로.
  예: `저장 실패가 조용히 넘어가던 문제 수정`
- **문서, 정리, 조사도 한 일이다.** 담백하게 적는다. 예: `실시간 로그 규칙 정비`, `인수인계 문서화`
- **끝나지 않은 것은 `~ 진행 중`** 으로 적는다.
- 오타, 포맷, 머지 같은 사소한 커밋은 빼거나 한 줄로 묶는다.
- **부풀리지 않는다.** 커밋이 말하는 것만. 성과나 효과를 지어내지 않는다.
- **쓰지 않는 것**: `소제목 — 세부` 구조, 가운뎃점, 괄호, 커밋 접두(`PROJ-12`, `fix:`), 엔지니어 수치(몇 배, 몇 초, ms, 화소). 제품 모델명은 괜찮다.

| | 예 | 왜 |
|---|---|---|
| ✗ 너무 세부 | `차트에서 구간을 클릭하면 해당 모듈 선택` | 엔지니어만 아는 조작 |
| ✗ 너무 세부 | `PLC 오류 응답 후 폴링이 영구 정지되던 것 수정` | 내부 동작 묘사 |
| ✗ 너무 뭉갬 | `관리 화면 사용성 개선` | 무엇을 했는지 안 보임 |
| ✓ 알맞음 | `장비 점검 화면에 모듈별 비교 표시 추가` | 대상, 내용, 끝말이 다 보임 |
| ✓ 알맞음 | `PLC 오류 시 연결 상태 표시 결함 수정` | 사용자가 보는 증상으로 씀 |

## 5. 내보내기 전 점검

- [ ] 블록마다 내용 줄 7줄 이하. 넘쳤으면 앞 6개와 `그 외` 한 줄인지
- [ ] 모든 줄 32자 이하
- [ ] 가운뎃점이 한 글자도 없다
- [ ] 줄표, 괄호, 커밋 접두, 파일명, 엔지니어 수치가 없다
- [ ] 같은 주제가 두 줄로 갈라져 있지 않다
- [ ] 줄마다 대상과 끝말이 있다. "~ 개선"만으로 무엇을 했는지 안 보이는 줄이 없다

## 6. 출력

붙여넣기 쉽게 **코드블록 하나**로 낸다. 줄머리 기호(`-`)는 **붙이지 않는다**
(사용자가 원하면 그때 붙인다 — 시트에 두 가지 스타일이 섞여 있다).

프로젝트가 하나면:

```
V/H 동시 표시를 렌더 오프셋 방식으로 재구현
실시간 스크롤 끊김 원인 규명 및 드립 정합 정리
수평 캔버스에 AI 탐지 목록 패널 추가
로그 오분류 재배치 및 로그 규칙 정비
```

프로젝트가 둘 이상이면 행이 나뉘므로 블록도 나눈다:

```
[DA 공통]
저장 이미지로 다시 돌린 AI 결과도 기록되도록 추가
AI 모델 선택 설정이 적용되지 않던 문제 수정
자동 업데이트가 다른 저장소를 바라보던 문제 수정
```
```
[SA 공통]
선명도 반경 설정 설명에 효과가 드러나도록 안내 문구 보강
```

기간을 요청받았으면 **날짜별로** 위 블록을 반복한다.

## 7. 마지막에 한 줄

출력 뒤에, 붙여넣을 텍스트와 **구분해서** 짧게 덧붙인다:

- 커밋으로 확인되지 않아 빠졌을 수 있는 작업이 있으면 그 사실
- 근거가 약해 추측이 섞인 줄이 있으면 어느 줄인지

시트의 다른 칸(카테고리, 상태, 성과)은 묻지 않으면 채우지 않는다.
